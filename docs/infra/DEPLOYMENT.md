# DEPLOYMENT.md: deploying LabOps Copilot

LabOps Copilot runs live on Render and Neon at https://labops.onrender.com. This
file is everything needed to stand it up again and every decision behind it,
written for someone who has not seen the conversation that produced it.

Read `docs/GAPS.md` first: it says what the system does not do.

---

## 0. Render and Neon, free and with no card

| Piece | Where | Why |
|---|---|---|
| API, worker, web | One Render free web service, one container (`deploy/`) | Render has no free background worker, so the three run as separate processes in one container; the worker still never serves HTTP |
| Redis | Render Key Value, free, private network only | `noeviction`, because BullMQ must never lose a queued job. No per-command quota, unlike free hosted Redis that idle BullMQ polling exhausts |
| PostgreSQL | Neon, free | Permanent. Render's free Postgres is deleted after 30 days plus a 14-day grace period |
| HTTPS, hostname | Render, `<service>.onrender.com` | Included |

`render.yaml` describes it; `deploy/start.sh` boots it: reset the demo database
(below), migrate, seed the demo operator (`SEED_OPERATOR_USERNAME=demo`), start
the three processes, then ingest the demo scenario through the real ingestion
path (`dist/seed-demo.js`). The demo routes stay off; nothing on the internet
can trigger a scenario. The script fixes `APP_ENV`, `SESSION_COOKIE_SECURE`,
`DEMO_ENABLED`, `TRUST_PROXY_HOPS`, `API_HOST` (127.0.0.1, so the API is
unreachable from outside), `API_PORT` and `API_INTERNAL_URL` after the
platform's environment, so the dashboard cannot contradict the production
checks; `CORS_ORIGIN` falls back to Render's `RENDER_EXTERNAL_URL`, and Next.js
listens on Render's `PORT`. Render's health check is `GET /login`. CI never
builds `deploy/Dockerfile`; Render builds it on every push to `main`.

**Verified live** (2026-10-16): the login page answers 200 over HTTPS and
reports `API: ok · PostgreSQL: up`, the five security headers are present, and
a warm page took about 0.27 s, measured from one client. The cold-boot and
memory figures below were measured locally under the same caps, not on the host.

**What this costs, plainly:**

- **It sleeps after 15 minutes without a request**, worker included. Locally,
  capped at 0.1 CPU, a boot took about 2.5 minutes to serve the login page
  (migrate, seed, then Next.js alone about 45 s). Warm it before showing it.
- **512 MB and 0.1 CPU** for three Node processes. Measured locally under the
  same caps: about 145 MB for the whole container, through a full incident
  journey. Each heap is capped anyway (`API_HEAP_MB`, `WORKER_HEAP_MB`,
  `WEB_HEAP_MB`).
- **Any process exiting stops the container**, so the platform restarts all
  three together rather than serving a site whose worker is dead.
- **750 free hours a month**, shared: exactly one always-on service fits.
- **Every boot starts from an empty database** (`DEMO_RESET_ON_BOOT=true` in
  `render.yaml`): `dist/reset-demo.js` drops the schema, then the boot migrates
  and seeds. A shared demo would otherwise stay resolved after its first
  visitor and age out of the dashboard's 7-day window. Anything a visitor did
  is gone after the service sleeps, so there is nothing to back up. The reset
  needs both `DEMO_RESET_ON_BOOT` and `APP_ENV=production`, and refuses,
  failing the boot, if any lab or event is not simulated; it drops the schema
  because the audit trail's triggers block deleting rows
  (`apps/api/src/modules/demo/reset.ts`).

**Standing it up:**

1. Neon: create a project in AWS Asia Pacific (Singapore), next to
   `render.yaml`'s `singapore`, the closest region to the expected audience
   (change both together if not; a Neon project cannot change region). Neon
   runs PostgreSQL 18; the integration suite passes on 18.6 as well as 16. Copy
   the **direct** connection string, not the pooled one: `prisma migrate
   deploy` takes an advisory lock.
2. Render: **New, Blueprint**, pick this repository. Enter `DATABASE_URL` and
   `SEED_OPERATOR_PASSWORD` (12+ characters) when prompted. `CREDENTIALS_KEY`
   is generated by Render.
3. Wait for the deploy, open `https://<service>.onrender.com`, sign in as
   `demo`.
4. Optional Google sign-in: add the four `GOOGLE_*` variables in the service's
   environment, with redirect `https://<service>.onrender.com/auth/google/callback`.

## 2. Why a serverless platform does not work

Three parts of the app need a long-running process, and it is worth writing
down so nobody retries it:

| Component | Why it needs a real host |
|---|---|
| `worker` (`node dist/worker.js`) | Consumes BullMQ queues forever. **Without it there is no correlation, no AI investigation and no recovery**: the entire product is the worker |
| `/api/events/stream` | Holds the response open and polls Postgres every second. Serverless functions have hard maximum durations, so the live dashboard would disconnect constantly |
| Migrations | `prisma migrate deploy` before the app starts. Not a function |

## 3. What makes a public deploy safe

Code changes, not configuration (#38), each of which matters only once a
stranger can reach the site.

**Investigation rate limiting.** `POST /api/incidents/:id/investigate` queues a
model call, the only route that can spend money. It is limited to 10 a minute,
in Redis, **failing closed** so a Redis outage refuses rather than allowing
unlimited calls. The limit is shared by every operator (next paragraph).
Reading results is deliberately not metered.

**`TRUST_PROXY_HOPS`.** Tells Fastify how many proxies to trust for the client
address. The deploy sets it to `1`, but it has nothing to act on today: the
browser reaches only the web server, which calls the API without forwarding the
client address. So the login and investigation limits are global
(`docs/GAPS.md` §2). Making them per person means forwarding `X-Forwarded-For`
from the web server.

**`APP_ENV=production` refusals.** The API fails at startup on:

- `SESSION_COOKIE_SECURE` not true: a Secure cookie over plain http is never
  sent, so nobody could sign in
- `TRUST_PROXY_HOPS` unset: a deploy must state its proxy hops explicitly
- `DEMO_ENABLED` true: demo routes must never ship

**Security headers** come from the web app itself (`apps/web/next.config.mjs`),
so they do not depend on a proxy in front of it.

## 4. Before it is genuinely public

1. **Access control.** One shared `demo` password. "Known users only" is true
   only once Google sign-in with an exact-email allow-list is configured
   (`AGENTS.md` §13a). **This is the real gate.**
2. **Uptime monitoring.** Nothing pings the site, and nothing alerts on an
   incident being created.
3. **Alerts on long open transactions.** The metric exists; nothing watches it.

The rest is in `docs/GAPS.md`.
