# LabOps Copilot

**AI-assisted incident correlation and safe recovery orchestration for cloud
lab operations.**

When many cloud training labs fail at once, an operations team has to work out
which failures share a cause, what that cause is, and how to fix it safely.
LabOps Copilot groups related failures into one incident, has an AI suggest
the likely cause, checks every suggested fix against fixed safety rules, and
lets a person approve it before anything runs. Then it confirms the fix
worked.

**Live demo: [labops.onrender.com](https://labops.onrender.com)**

- Sign in as `demo`. The password is shared with the project submission.
- It runs on a free plan that sleeps after 15 minutes without a visit, so the
  first visit can take a few minutes to wake up. After that, pages load in well
  under a second.
- Every wake-up starts a fresh demo. If an incident is already resolved when you
  arrive, someone used it recently; it will be fresh after the next sleep.

> **Everything here is simulated.** The labs, their failures and the fixes are
> generated by the project itself. It connects to no real cloud or lab
> platform, so nothing it does can affect real infrastructure.

## The problem

A single failed lab is easy. Thirty failing at once is not: they might share
one root cause, or be three unrelated problems that happen to look alike.
Fixing the wrong thing, or the right thing twice, makes it worse.

LabOps Copilot shows one way to handle that, in eight steps:

1. **Group** related failures into one incident, and say why each one belongs.
2. **Investigate** the incident with AI, using only evidence the system picked.
3. **Suggest** a fix, chosen from a short list of known, safe actions.
4. **Check** the fix against fixed rules. The AI has no say here.
5. **Approve**: a person decides.
6. **Run** the fix in the background, exactly once.
7. **Confirm** the labs actually recovered before closing the incident.
8. **Record** every step in a history that cannot be edited.

## Try it

Sign in to the [live demo](https://labops.onrender.com). It already holds 55
simulated labs from two scenarios: 12 labs that failed together because of one
shared image registry, two smaller outages, and failures that only look
related. The steps below follow the 12; [every path](#every-path-one-incident-each)
lists what each of the other incidents shows.

1. **Overview.** Counts, a failure timeline and labs by state. The burst of 12
   is the tall bar. Light and [dark](docs/images/dashboard-dark.png) themes
   follow your system, or switch with the toggle in the header.
2. **Incidents.** The 12 related failures are one incident; the unrelated ones
   stay separate. Grouping uses fixed rules, never the AI, so it is the same
   every time.
3. **Open the 12-lab incident.** Each lab shows why it was included and how
   strongly it matched. The timeline on the right is its full history.

   ![An incident resolved after approval](docs/images/incident.png)

4. **Investigate.** The AI returns a likely cause, the evidence behind it,
   what is missing, its confidence, and a suggested fix: retry provisioning on
   those 12 labs. On the live demo the AI is a deterministic stand-in, so every
   run gives the same answer; a real model is an opt-in setting.
5. **Approve.** The safety rules have passed, so the fix waits for you. Approve
   it and watch: the system re-checks the rules, runs the fix, confirms each
   lab recovered, and only then resolves the incident. The page updates on its
   own.
6. **See a refusal.** Open a permission-denied incident and investigate. The AI
   suggests a retry, but retrying cannot fix a permissions problem, so the
   rules block it and say why. Nothing is offered for approval.

   ![A suggested fix blocked by the safety rules](docs/images/policy-blocked.png)

7. **Audit.** Every step, with who or what did it and when.

### Every path, one incident each

Each incident on the demo takes a different route through the safety rules.
Open it from **Incidents** and do what the middle column says.

| Incident | Do this | What you should see |
|---|---|---|
| **PROVISION_TIMEOUT on image-registry** (12 labs) | Investigate, then Approve | The fix passes the rules and waits for you, with a 30-minute countdown. Approved, it runs, every lab is checked, and the incident closes. |
| the same, instead | Investigate, then Reject, or leave it 30 minutes | Nothing runs. A rejection reopens the incident; an expired approval sends it to a person. Either way, Investigate again for a fresh suggestion. |
| **PERMISSION_DENIED** (any of 4) | Investigate | The AI gets it wrong and suggests a retry. The rules refuse it: a retry cannot fix missing permissions. |
| **NETWORK_CONFIG** (any of 3) | Investigate | One failure on its own is not enough to go on, so the AI suggests nothing. |
| **DEPENDENCY_UNAVAILABLE on license-server** (6 labs) | Investigate, then Approve | The AI suggests re-checking the license server. You approve, it runs, and the check still fails: checking a server does not fix the labs. The incident stays open for a person. |
| the same, straight after | Investigate again | The same check is refused: it ran less than 5 minutes ago. |
| **QUOTA_EXCEEDED on subscription-quota** (5 labs) | Investigate | No safe automatic fix exists, so the AI hands it to a person. Nothing is offered for approval. |
| **PROVISION_TIMEOUT on artifact-cache** (two incidents) | Open both | Same error, same cache, but 25 minutes apart, so they are kept separate. One says how close it came to joining the other. |

Some failures cannot be triggered from the demo, because its AI stand-in
always answers correctly formed: a model that times out or returns garbage, one
that names a lab outside the incident, text in a log trying to give the AI
orders, two people approving at once. Each has an automated test; the
[acceptance map](docs/specs/labops-copilot/ACCEPTANCE.md) names them.

## How it keeps AI safe

The central idea: **the AI suggests, fixed rules decide, a person approves.**

- **The AI cannot act.** It can only suggest one of a few predefined fixes.
  There is no way for it to run a command or invent an action.
- **Its answers are checked, not trusted.** A malformed or out-of-bounds answer
  is rejected, and the incident is left exactly as it was.
- **Text in logs is treated as data.** A log line saying "ignore your
  instructions" has no effect.
- **Approval is not a blank cheque.** Just before a fix runs, the rules are
  checked again against the current state, and approvals expire.
- **Nothing runs twice.** A double click or a repeated message produces one
  fix, not two.
- **"Fixed" means checked.** An incident closes only when every lab is
  confirmed healthy, not when the fix was merely sent.

## Built with

TypeScript throughout: a **Next.js** dashboard, a **Node.js** API and a
background worker, **PostgreSQL** for the data, **Redis** for the job queue,
and an AI model behind a strict output check (a deterministic stand-in on the
live demo; a real model is opt-in, see
[docs/dev/SETUP.md](docs/dev/SETUP.md)). Tested with **Vitest** and
**Playwright**, run with **Docker**, deployed on **Render** with **Neon**.

The full list and the reasoning behind each choice are in
[docs/dev/DESIGN.md](docs/dev/DESIGN.md).

## Run it yourself

With Docker installed:

```bash
echo "SEED_OPERATOR_PASSWORD=$(openssl rand -hex 16)" >> .env
docker compose up --build
```

Open `http://localhost:3000`, sign in as `operator` with the password from
`.env`, and click **Run demo scenario**. Every other way to run it is in
[docs/dev/SETUP.md](docs/dev/SETUP.md).

---

## What it does not do

- **It connects to no real lab platform.** Every lab comes from its own
  simulator.
- **Recovery is simulated.** Approving a fix changes the labs in this
  project's database, not real infrastructure.

These are deliberate, and [docs/GAPS.md](docs/GAPS.md) lists every limit
plainly.
